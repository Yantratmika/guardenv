Why guardenv

Secrets want to live with the code. Git doesn't want them there.

Every project has a .env. Every team has a different, slightly awkward way of sharing it.

The problem

A .env file carries the things your app cannot run without: API keys, database passwords, tokens. It must not be committed in plain text, so it is git-ignored. And that creates a different problem: the file now lives outside your repository, and has to be passed around by hand.

  • New teammate, day one. "Can someone send me the .env?" It arrives by chat or email, is probably out of date, and now sits in a message history forever.
  • Many projects. People work on many repositories, for different teams. Secrets scattered across chats, notes and desktop folders get lost, mixed up, or reused where they shouldn't be.
  • Drift. Someone adds a variable. Half the team does not know, and spends an hour on a failing build.
  • Accidents. The cost of the other extreme, committing the plaintext file once, is high. Secrets stay in Git history even after you delete the file.

Setting up a full secrets platform is the textbook answer, but it is heavy for many projects and small teams. People want everything about the project in one place.

How guardenv helps

guardenv gives you that one place: the repository. The secrets travel with the code, but only in encrypted form.

One source of truth

The encrypted guarded.env is versioned with the code. A change to a variable is a normal commit, with history and review.

Zero-effort onboarding

Clone, drop in the key once, and the right .env appears. After that, pulls keep it current.

Safe by default

.env is kept in .gitignore, and the commit hook encrypts before anything is recorded.

No servers, no accounts

A single command-line program and a key file. Nothing to host, sign up for, or pay for.

Who it is for

  • Small teams and open collaborators who share development and staging credentials.
  • Consultants and freelancers who juggle several client projects on one laptop.
  • Monorepos with several .env files in different folders.
  • Anyone tired of hunting for "the latest .env".

What it is not

Being clear about limits is part of using any security tool well.

  • One shared key per project. Anyone who has the key can decrypt every guarded file. There are no per-person permissions.
  • No key rotation yet. If a teammate leaves, rotate the secrets themselves (the API keys and passwords), and consider creating a new key. Older commits remain readable with the older key.
  • Your key is your responsibility. It is stored as a file in your home folder. If it is lost, the encrypted files cannot be recovered.
  • Not for production. For production workloads, use your cloud's secrets manager. guardenv is for development and shared project configuration.
  • It does not hide secrets on your machine. The decrypted .env is a plain file, as it always was.
