How guardenv works

A single Go program with no dependencies beyond the standard library. The full source is one file you can read in an evening: main.go on GitHub.

View the repository

The pieces

WhatWhereCommitted?
Plain secrets.env, .env.local, … in any folderNo (git-ignored)
Encrypted secretsguarded.env next to each .env (.env.local becomes guarded.env.local)Yes
Project config.guardenv/configYes
The key~/.guardenv/<secret-name>Never

The config is plain JSON. It names the key file and lists the guarded files:

{
  "secret": "myproject-3f9c1a7d2b8e4a10",
  "files": [".env", "api/.env"]
}

guardenv init

  1. Makes sure .env and .env.* are in .gitignore (and !.env.example, so templates stay committable).
  2. Walks the repository looking for .env and .env.* files. It skips .git and any directory Git itself ignores, such as node_modules. Files named .example, .sample, .template or .dist are left alone.
  3. Generates a random 32-byte key and saves it as hex to ~/.guardenv/<project>-<random>, readable only by you. The unique name stops two projects clashing. If the project already has a config, the existing key is reused.
  4. Writes .guardenv/config.
  5. Installs the git hooks.

Encryption

Each file is encrypted with AES-256-GCM from Go's standard crypto library. GCM is authenticated encryption: it hides the content and detects tampering or a wrong key, instead of returning garbage.

guarded.env =  "GUARDENV1\n"  ||  nonce (12 bytes, random)  ||  ciphertext + auth tag
               └─ header, also bound in as authenticated data
  • A fresh random nonce is used every time a file is encrypted.
  • If a guarded.env already decrypts to exactly the current .env, it is left untouched, so Git history is not filled with meaningless changes.
  • Decryption fails with a clear error if the key is wrong or the file has been modified.

Git hooks

Hooks are installed into the repository's own hooks folder, so they apply to that repository only.

HookCommandWhen
pre-commitguardenv encrypt --stageJust before every commit: encrypts each .env, then git adds the guarded.env files so they are in that commit. If this fails, the commit is blocked.
post-checkoutguardenv decryptAfter clone and branch switches.
post-mergeguardenv decryptAfter git pull or merge.

If a hook file already exists, guardenv appends a marked block (# guardenv-managed) and never overwrites your own hook logic. Running install-hooks again does not duplicate it. Git does not share hooks between clones, so each teammate runs guardenv install-hooks once per clone.

Decrypting safely

  • If .env is missing, it is created from guarded.env (permissions limited to you).
  • If .env already exists and matches, nothing happens.
  • If .env exists but differs, guardenv keeps your local file and prints a warning, so a pull never destroys unsaved edits. Run guardenv decrypt --force to overwrite.

Release automation

guardenv is released with no manual build steps. Pushing a version tag does everything:

git tag v0.1.0
git push origin v0.1.0
    ↓
GitHub Actions starts the "release" workflow
    ↓
GoReleaser cross-compiles Windows, Linux and macOS (amd64 + arm64),
embeds the version, and writes checksums.txt
    ↓
A GitHub Release is created with the archives attached
    ↓
A Scoop manifest is pushed to the scoop-guardenv bucket
    ↓
scoop install guardenv  /  scoop update guardenv

The workflow and configuration are in the repository: release.yml and .goreleaser.yaml.

Command reference

CommandWhat it does
guardenv initSet up the project: gitignore, config, key, hooks.
guardenv encrypt [--stage]Encrypt each .env to guarded.env. --stage runs git add on the results.
guardenv decrypt [--force]Decrypt each guarded.env to .env.
guardenv install-hooks(Re)install the git hooks.
guardenv versionPrint the installed version.
